# memory agent 的基础知识与近期研究结合方案

2026-10-24。面向三年 Java 后端转 Agent 应用开发的求职准备。

结论：这个项目可以作为基础学习和技术面讲解的主线。现有结构化抽取、记忆更新、检索、作业和删除验证提供了可读代码；再加入一个受控的工具决策循环，以及公平的评测，能把知识串成完整案例。近期研究应转化成小实验和设计取舍，不必同时引入所有框架。

本次核对 README、项目说明、核心源码、数据库定义、测试实现和结果文件，并阅读截至本日可访问的一手资料。现状判断来自静态代码；没有启动服务、运行数据库测试或调用付费模型。以下增强项均为建议，未修改业务实现。

## 一 当前项目能证明什么

项目更准确的现阶段定位是“使用模型进行抽取与更新决策的长期记忆后端”。输入、抽取、更新、检索、回答的主路径由程序控制；模型在其中做结构化判断。Pydantic AI 中创建了三个 Agent 对象，不自动等于三个自主协作 Agent。

代码中可以确认 output_type 和 run_sync 的使用，但没有发现供模型自主选择的业务函数工具注册。结构化输出底层可能使用工具调用协议，这与能多轮选择搜索、查历史、核对证据的业务 Agent 循环仍有区别。[Pydantic AI 工具与结构化输出说明](https://pydantic.dev/docs/ai/tools-toolsets/tools/)

本地结果文件记录 2026-10-23 离线 38 条单元/集成及 20 条回归通过，live 20 条回归通过；这是历史报告，不是本次复跑。离线回归注入金标抽取与规则模型，适合检查程序逻辑，不能作为模型质量成绩。live 回归中的若干断言检查关键词出现，尚不能充分衡量答案语义和证据支持。

## 二 把基础知识直接对应到代码

| 基础知识 | 现有落点 | 接下来应亲自解释或验证 |
|---|---|---|
| 模型 API 与结构化输出 | `llm.py`、`schemas.py`、`engine.py:21` | Schema 能约束什么，业务代码还需要校验什么；失败与重试怎样处理 |
| Prompt 与上下文工程 | `prompts.py`、`engine.py:83` | 为什么提供最近 10 轮及已有事实；哪些信息不该放入；压缩后会丢什么 |
| Embedding 与 RAG | `embedding.py`、`recall.py:28` | 相似度阈值怎样选；实体名、数字和否定词为什么容易出问题 |
| 记忆写入与冲突 | `engine.py:125`、`engine.py:180` | ADD、INVALIDATE、NOOP 各自条件；兼容偏好不能随便覆盖 |
| 时间与历史 | `migrations/001_init.sql`、`recall.py:50` | 事实何时成立与系统何时获知如何区分；追溯查询如何过滤 |
| 异步与幂等 | `store.py:38`、`jobs.py:19`、`engine.py:236` | 同一输入、同一作业、同一业务事实分别怎样去重 |
| 故障恢复与并发 | `jobs.py:39`、`jobs.py:47` | 租约过期后旧 worker 还能否提交；恢复执行需要哪些状态 |
| 可验证删除 | `deletion.py:23`、`deletion.py:84` | 删除范围是单条版本链还是整个事件；哪些存储与派生内容要覆盖 |
| 评测与可观测 | `tests/regression/test_regression.py:56`、`tracing.py` | 行为检查与模型质量分开；如何从一次错误追到抽取或检索阶段 |

文档知识库中的 PDF 解析、长文档切块、OCR，当前项目也没有覆盖。无需为了“覆盖所有知识”硬塞进来；工作知识库项目可以承担这部分。训练、GPU 推理和浏览器操作同样不是这个项目的必要范围。

## 三 先把现有能力的边界讲准确

### 时间字段已经存在 追溯查询尚未完成

`recall.py:69` 调用 `retrieve` 时没有传入 `as_of`；`retrieve` 在第 37 行只过滤 `status='active'`。`as_of` 在第 92 行作为提示词里的 today 使用。因此可以说有版本链和时间字段，但还不能说已实现完整双时间轴历史查询。

适合练的设计：把“事实在何时有效”与“系统截至何时知道这件事”拆成两个参数，并明确默认语义。例子：24 日收到一条更正，说明 20 日发生的安排有误；要能区分“按现在掌握的信息，20 日真实安排是什么”与“站在 21 日系统当时知道什么”。后者不能泄露 24 日才获知的内容。事件发生日期也不一定等于这条陈述开始有效的日期。

### 有引用 ID 不等于回答有依据

`recall.py:101` 至 106 行会移除不在候选集合中的引用 ID，但当 abstain=false 且过滤后 ID 为空时，仍可能保留答案。应增加“无有效证据如何处理”的明确契约，并对重要结论核对来源。单纯保证 ID 存在也不能证明证据支持结论。

更新器收到无效 target 时回退为 ADD（`engine.py:125` 所在函数），可能保留互相冲突的新旧事实。可比较有限重新决策、拒绝更新、进入待核实等方案；不要仅把格式错误转成新增就视为问题解决。

### 有空间过滤 还不是身份认证

API 使用调用方提供的 `X-Owner-Id`，来源类型也在请求体中传入，适合本地演示。上线前身份要来自可信认证，数据来源信任级别要由服务端接入路径决定；`GET /jobs/{id}` 也需要校验归属。不能把“换一个 owner 头得到另一个空间”当作已验证的多用户安全。

### 作业租约和数据库事务仍可深入

`engine.py:245` 的事务包含模型调用。可学习“事务外读取与决策，短事务内复核版本并提交”，但同时要处理删除、并发更新和过期任务。单把模型调用移到外面会引入新的竞态，必须重新检查来源是否已删除、版本和任务所有权是否仍有效。

`jobs.py` 的完成和失败更新主要按作业 ID，未看到提交时校验领取者和租约代次。下一步可以用领取 token 或 generation 做 fencing（拒绝旧执行器提交），设计一个旧 worker 延迟返回的测试。是否已发生实际错误需要运行验证，本次只是识别需要验证的边界。

### 删除验证有明确检查范围

`deletion.py:55` 明确保留同一原文派生的其他版本链；因此“删除一张卡片”和“忘掉整个事件”是不同能力。关键词、向量阈值和残留行检查能发现部分残留，不能证明所有表达方式、缓存、备份、第三方日志和模型侧数据均被清除。

适合新增的学习题是明确删除范围、派生依赖与重新写入规则。用户有意重新告诉系统一件事，应与旧任务在删除后偷偷重新写回区分。反思生成的推断、摘要和索引未来也要加入删除依赖。

## 四 近期领域知识怎样落进来

### 方向一 多路检索与事实之外的原始证据

[Hindsight 的 ACL 2026 演示论文](https://aclanthology.org/2026.acl-demo.27/)在 2026 年 7 月介绍了 retain、recall、reflect，以及向量、关键词、图关系和时间过滤的组合。可借鉴“不同检索方式解决不同遗漏”，先不复制完整系统。

当前 `recall` 只检索事实向量。项目已经写入 `episode_round` 检索键（`engine.py:265`），但回答路径没使用它们。可以比较：事实向量；事实加原文检索；再加中文关键词及实体/时间过滤。第一版用合并去重和简单排名融合即可，重排模型等有明确误差再引入。

特别适合的案例：事实抽取丢掉一句限制条件，而原文保留了；查询含准确公司名、数字或“不接受”的否定偏好。若原文检索开放给低信任材料，必须保留来源标记，不能顺便把它升级成长期可信事实。

知识收益：Embedding、混合检索、排名融合、重排、来源可信度、召回与作答分层评价。

### 方向二 事实 观点与反思记忆分开

Hindsight 区分事实、经历、观察和观点，为“模型推断不等于用户明确陈述”提供了参考。可以给本项目增加最小的事实类型与来源，而不是立即建设复杂知识图谱。

例如“用户明确说偏好中文沟通”是陈述事实；“用户可能更喜欢小团队”若由多段对话归纳，就是可撤销的推断。记录推断依赖哪些证据、何时生成、是否过期；证据删除或被纠正时，推断必须重算或作废。模型自报 confidence 不能直接当作校准后的正确概率。

第一版只读展示反思候选，不自动让推断覆盖用户原话。用用户明确否定推断的样例检查纠错能力。

知识收益：记忆类型、信息来源、置信度校准、更新策略、派生依赖与删除传播。

### 方向三 记忆写入成本和信息保真度

2026-10-01 的预印本 [MemFit](https://arxiv.org/abs/2610.00872)关注昂贵记忆构建的问题，提出保留原始轮次、以摘要作为索引而不替换原文，并结合多路检索。这里借鉴摘要中的问题与设计方向；未复现其效果。

你的项目已把用户写入与后台抽取分开，但总成本仍包含后台模型调用。实验可以比较：每轮结构化抽取；原文直接检索；原文与精选事实并存。统计热路径延迟之外的记忆可用等待时间、后台费用、存储和查询费用。

统一比较相同资料、相同问答模型、相同测试集、相同上下文预算。不能拿“异步返回很快”证明“整体写入成本低”，也不能把只存原文视为天然优于抽取。

知识收益：异步架构、Token 成本、信息压缩损失、索引设计与质量成本取舍。

### 方向四 时序记忆与知识图谱

[Zep 论文](https://arxiv.org/abs/2501.13956)发表于 2025 年，属于已有基础路线，不应包装成今年新发明；[Graphiti 当前实现说明](https://github.com/getzep/graphiti)提供事实有效期、历史关系和来源追溯的参考。

最直接的结合是补齐前述时间查询和实体归一。先用现有 PostgreSQL 表实现并测试；只有“多个人、项目、组织的关系需要多跳查询”成为实际问题，再评估图结构和图数据库。双时间轴字段本身不等于实现 Graphiti，也不证明具有其研究效果。

知识收益：时间语义、实体消歧、版本化、关系检索，以及何时不需要额外数据库。

### 方向五 从对话事实记忆到任务经验记忆

[LongMemEval 原版](https://github.com/xiaowu0162/LongMemEval)适合评估信息抽取、跨会话推理、知识更新、时间推理和弃答。官方还发布了 [LongMemEval V2](https://github.com/xiaowu0162/LongMemEval-V2)，聚焦 Agent 在环境中的长期经验，包括状态变化、工作步骤、常见失败和错误前提。这两个版本的任务不同，成绩不能直接混用。

当前项目先做原版方向的评测更合适。以后可以扩展少量 procedural memory（任务经验）：保存某个工具在什么前提下有效、遇到什么错误、采用什么修复、最后是否验证成功。下次相似任务检索这段经验，检查能否减少失败。经验应绑定环境和版本，工具升级后可能失效。

不要把“模型写了一段复盘”直接当学习成功；要在未见过的相似任务上比较有无这段经验。这项放在第三阶段，当前无需下载庞大的完整 V2 数据集。

补充基础对照：[Mem0 2025 论文](https://arxiv.org/abs/2504.19413)可用来理解抽取、整合、检索的常见路线。它不是最新论文，也不是要求替换当前实现的依据。

## 五 补一个能体现 Agent 的受控循环

建议继续使用现有 Pydantic AI 与 PostgreSQL。先加入三个只读业务工具，不把删除和任意写库直接交给模型：

| 工具 | 做什么 | 关键约束 |
|---|---|---|
| search_memories | 按问题、实体、空间和时间检索 | 用户身份服务端注入，不允许模型改 owner |
| get_memory_history | 查询某个事实的版本变化 | 遵守查询时间和访问权限 |
| get_source_evidence | 读取相关原文或原始轮次 | 只取未删除、获授权的证据，并保留信任标签 |

用户问：“我最初的要求是什么，后来改了哪些，现在应该按哪个执行？”模型先搜索当前记忆，发现版本变化后查历史，需要验证时看原文，最后回答或说明缺少哪项信息。它根据观察选择后续工具，程序控制最多轮数、总耗时、费用与权限。

可以把每个工具结果存入任务记录，支持故障后继续；对相同工具和参数的无进展重复调用提前终止。先做这个有限循环，无需引入复杂 planner、多 Agent 团队或新的编排框架。

MCP 是后续接入形式：当想把三个能力给外部助手复用时，再暴露为 MCP 服务。MCP 接通并不自动增加记忆质量，也不应作为循环是否有效的替代证据。

## 六 用实验把知识变成面试证据

先固定一批不参与调参的任务，并明确最终验收，再做下列对照。建议数字是实验规模起点，不是已完成结果。

| 实验 | 对照方法 | 交付证据 |
|---|---|---|
| 记忆是否有用 | 最近 N 轮、原文向量检索、当前结构化事实；全历史在同一上下文预算内可行时补充 | 答案正确、证据支持、弃答、费用和延迟 |
| 混合检索是否有用 | 同一批任务，纯向量 vs 事实与原文加关键词 | 各类错误的召回变化，不只总分 |
| 时间查询是否正确 | 当前查询、按事实有效时间、按系统知晓时间 | 无未来信息泄露，迟到更正与乱序写入案例 |
| 工具循环是否值得 | 固定单轮检索 vs 最多三轮自适应检索 | 跨会话/改期题成功变化，以及额外轮次和费用 |
| 记忆治理是否可靠 | 删除单条链、整个事件、派生推断；并发写入与删除 | 范围明确、残留与重新写入测试、超时恢复 |

保留现有 20 条中文回归作开发检查，再增加独立用例。可先选 30–50 条分层的 LongMemEval 原版样本验证适配，但必须称为子集，不报告为全量 benchmark。重复运行并报告波动；固定模型、提示、检索参数、数据版本和预算。

当前默认中文 embedding 与原版英文数据不直接匹配：用原版数据时，应选适合该语言的嵌入模型；自行翻译后需人工校验，并标明是改编集。助手消息与用户消息的来源策略也会影响结果，不能为提高分数把所有内容都伪装成用户的可信陈述。检索输入不能包含 gold answer、has_answer 或 evidence 标签；oracle 只用于隔离诊断，不能当端到端成绩。

回答评价补充完整结论与证据一致性，避免“出现正确日期但整句话说错了”仍通过。测写入、检索、回答的分项成本，初次模型加载和稳态延迟分开。各论文分数不是本项目能达到的承诺。

## 七 实施和学习顺序

| 顺序 | 做什么 | 对应面试主线 |
|---|---|---|
| 第一轮 | 读通现有代码，明确时间/引用/身份/删除的契约，固定回归与对照样本 | 模型输出如何被可靠的软件约束 |
| 第二轮 | 补时间检索与证据检查，处理短事务和过期 worker；再做混合检索实验 | 为什么系统在更新、失败、并发时仍正确 |
| 第三轮 | 增加三个只读工具和受控循环，用独立样本比较单轮与多轮 | Agent 为什么选择这一步，怎样证明额外成本有价值 |
| 后续可选 | MCP 接入，事实与推断分离，少量任务经验记忆 | 标准集成、来源治理、跨任务学习 |

每轮顺序是建议，具体耗时要按现有依赖和失败样例确认。现有 Python 项目无需仅为“我主业 Java”整体重写。可以把数据库事务、作业队列和幂等设计与 Java 工作经历对应；目标岗位确需 Java 集成时，再加一个小客户端示例即可。

最终适合讲的项目故事是：用户信息会更新、互相矛盾和被删除，我如何控制写入、提供可追查证据、保证恢复与隔离，再用有限工具循环改善复杂问题，并通过对照实验说明收益。这比堆叠框架名更能支撑技术追问。
